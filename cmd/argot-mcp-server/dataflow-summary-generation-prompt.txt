# Dataflow Summary Generation Task

You are tasked with generating dataflow summaries for Go functions to be used with the Argot taint analysis tool. A dataflow summary describes how data flows through a function - which inputs affect which outputs.

## Dataflow Summary Format

Generate summaries in YAML format using this structure:

```yaml
dataflow-summaries:
  - package: "<package name>"
    function: "<function name>"  # for standalone functions (cannot have receiver or interface field)
    receiver: "<struct name>"    # for methods (with method field, cannot have function field or interface)
    interface: "<interface name>" # for interface methods only (cannot have receiver or function fields)
    method: "<method name>"      # for methods only
    flows:
      - from: "<source>"
        to: "<destination>"
```

The receiver name also indicates whether the receiver is a pointer to the type or a value. For example, if I have a function `func (f *FD) OpenDir() (...)` then `receiver: *FD` (i.e., the local type name with a pointer).

## Flow Identifiers

Use these identifiers to specify data flow sources and destinations:

- `!arg 0`, `!arg 1`, etc. - Function arguments by position, the position is not between delimiters.
- `!arg <name>` - Function arguments by name, must be between < and >. You can also use `!arg <name 0>` to combine position and name.
- `!receiver` - Method receiver (methods only), interface receiver (interface method)
- `!ret`, `!ret 0`, `!ret 1`, etc. - Return values by position (this is the tuple position)

For methods, argument indexing starts after the receiver:
- In `func (r Receiver) method(x, y int) string`, `x` is `!arg 0`, `y` is `!arg 1`

## Complex Data Flows

For flows through struct fields, use parentheses and suffixes:

- `(!arg 0).field` - Flow through struct field
- `(!arg <x>).field1.field2` - Nested field access

The maximum access path length is 3 (e.g. `a.b.c`).

Field-sensitivity exists to *distinguish* fields that behave differently -- it is not a requirement
to enumerate fields whenever a struct is involved. If every field of an input flows to the same
output (or set of outputs) the same way, describe that with one field-insensitive flow (e.g. `!arg 0`
to `!ret 0`) rather than one line per field. A field-sensitive flow is only worth writing when it says
something a coarser flow couldn't: that this field goes somewhere others don't.

Embedded (anonymous) fields need the fully qualified access path, named after the embedded type --
the same name Go source uses only when *declaring* the field, not the promoted name used to *access*
it. For
```go
type Base struct { X int }
type Outer struct {
    Base
    Y int
}
```
the correct path to `X` is `(!arg 0).Base.X`, not `(!arg 0).X`, even though ordinary Go source may
access `outer.X` (promotion), never mentioning `Base`. Always check the actual struct declaration
(via `go doc -src -u`, per "Workflow" below) rather than inferring field names from how the source
accesses them.

We do not support tracking flows through individual elements of arrays, slices, maps, or channels. If a single element of an array/slice/map/channel gets tainted, the entire array/slice/map/channel gets tainted.

## Interfaces

For flows to or from interface types (e.g. `fmt.Stringer`), use a field-insensitive identifier (e.g.
`!arg 0`). Interfaces do not have fields. Use field-insensitive identifiers even if the function
implementation uses the concrete type of an interface at run-time (i.e., through a type switch), and
even if every possible implementation happens to share a field of the same name: the checker has no
way to represent that a position is field-sensitive only for certain types, so any such summary will
be rejected as unsound no matter how the implementations line up.

This applies wherever an interface-typed position occurs, not just whole top-level arguments:
- A struct field of interface type: stop at that field and go no deeper, e.g. `(!arg 0).Handler` but
  never `(!arg 0).Handler.something`.
- A receiver or return value of interface type: use `!receiver` or `!ret 0` directly, with no suffix.
- This applies through named types and pointers wrapping an interface, not just literal
  `interface{...}` syntax: if the underlying type is an interface, treat the position as
  field-insensitive regardless of its static type.

E.g., for the following method `(*Rec).F`, the only valid summary is `!arg 0` flows to `receiver`,
even though there is a type switch, and even though `impl1` and `impl2` share an identically-named
and identically-typed field `f`:

```go
type iface interface { impl() }
// impl1 and impl2 are the *only* types that implement iface
type impl1 struct { f int }
func (*impl1) impl() {}
type impl2 struct { f int }
func (*impl2) impl() {}

type Rec struct { a int; b int }

func (r *Rec) F(i iface) {
    switch it := i.(type) {
    case impl1:
        r.a = it.f
    case impl2:
        r.a = it.f
    default:
        panic("unreachable")
    }
}
```

## Task Instructions

1. **Analyze the function**: Understand what the function does and how data moves through it and its callees
2. **Identify flows**: Determine which inputs affect which outputs
3a. **Be precise**: Only include input->output data flows that actually exist
3b. **Be sound**: Include all possible input->output data flows
3c. **When precision and soundness conflict**: prefer the more precise (narrower) flow unless you
    have a concrete reason to believe a broader flow exists -- don't pad a summary with flows
    "just in case." A summary that's too broad is as unhelpful as one that's wrong.
3d. **Don't fragment a flow that isn't actually field-sensitive**: per the field-sensitivity note
    under "Complex Data Flows" above, if every field of a struct input flows to the same output the
    same way, write one field-insensitive flow instead of one line per field.
3e. **Never omit a flow because the data seems unimportant, non-sensitive, or "not meaningful"**:
    a dataflow summary is a mechanical description of what data reaches what output, not a judgment
    about which of those flows a security review would care about. Whether a value is a retry delay,
    a timestamp, a byte count, or a piece of user credentials is completely irrelevant to whether the
    flow belongs in the summary -- only "does this input's data actually determine that output's
    value" matters. Reasoning like "this is just metadata, no meaningful taint flow needed" is never
    a valid basis for leaving a flow out; if the data flows, include it, full stop. Downstream tools
    that consume this summary decide what is sensitive; the summary's only job is to be accurate.
4. **Consider all paths**: Account for all execution paths (branches, loops, error cases)
5. **Handle mutations**: If arguments are modified, include flows back to them

## Workflow

You are effectively simulating a dynamic taint analysis. Taint applies to access paths, not whole
values: e.g., a struct argument's fields can each be tainted independently (up to the maximum access
path length of 3 from "Complex Data Flows" above). For each tainted access path in the function
body, follow it into every call it's passed to, and determine how that call's own inputs affect its
outputs, before deciding whether taint continues past that call. This is recursive -- a callee's own
callees may need the same treatment. Don't follow taint flows into global variables since they are
not represented in the summary format.

- Use `go doc -src -u`/`argot_show_src` (plain Go source) to read the source code of the function.
- For tainted inputs (e.g., function parameters or the receiver) or outputs (e.g., return values or
  the receiver), if its type is named, use `go doc -src -u <TypeName>` to see the specific struct
  fields -- `argot_show_src` only shows function bodies, not type declarations, so it can't answer
  this. If the type is an interface, do not specify any fields.
- For each call that receives a potentially-tainted access path, inspect that callee's source
  the same way you would the top-level function, and repeat as needed.
- Stop recursing into a call once you're confident of its behavior from its signature/doc comment
  alone (e.g., well-known standard library functions like `fmt.Sprintf`, `strings.TrimSpace`), or
  once you've already generated a summary for it in this session.
- Fall back to `argot_show_ssa`/`argot_show_ssa_value` only when source alone leaves real
  ambiguity about exactly which struct field/value a line of source touches.
- If a call's behavior is genuinely unclear after inspection (e.g. it's a large, unfamiliar
  function you can't fully trace), don't guess -- fall back to the safer, sound-but-coarser flow
  (e.g., treat the whole return value as tainted) rather than omitting the flow entirely.

## Examples

**Simple function:**
```go
func concat(a, b string) string {
    return a + b
}
```
Summary:
```yaml
dataflow-summaries:
  - package: "mypackage"
    function: "concat"
    flows:
      - from: "!arg 0"
        to: "!ret 0"
      - from: "!arg 1"
        to: "!ret 0"
```

**Method with field access:**
```go
func (u *User) GetFullName() string {
    return u.FirstName + " " + u.LastName
}
```
Summary:
```yaml
dataflow-summaries:
  - package: "mypackage"
    receiver: "User"
    method: "GetFullName"
    flows:
      - from: "(!receiver).FirstName"
        to: "!ret 0"
      - from: "(!receiver).LastName"
        to: "!ret 0"
```

**Function modifying arguments:**
```go
func appendToSlice(slice []string, item string) []string {
    slice = append(slice, item)
    return slice
}
```
Summary:
```yaml
dataflow-summaries:
  - package: "mypackage"
    function: "appendToSlice"
    flows:
      - from: "!arg 0"
        to: "!ret 0"
      - from: "!arg 1"
        to: "!ret 0"
```

**Interface method summaries** are dataflow summaries that hold for all implementations of a given interface method. For example, the following summary should hold, since all `String()` methods should just result in flows from the receiver to the returned value:
```go
dataflow-summaries:
  - package: "fmt"
    interface: "Stringer"
    method: "String"
    flows:
      - from: "!receiver"
        to: "!ret 0"
```

Interface method summaries are *not* field-sensitive.

## Important Notes

- **Precision vs. soundness**: prefer precise flows; see "When precision and soundness conflict" above for the tiebreaker
- **Error handling**: Consider flows through error return values in Go's `(result, error)` pattern
- **Mutations**: If the function modifies input arguments, include flows back to them
- **All execution paths**: Consider branches, loops, and error conditions

## Analysis Tools Available

Use the following argot analysis tools to understand a function and its callees. Tracing is
recursive, not a fixed sequence -- expect to revisit these tools for each callee you inspect.

0. **`argot_reload_config`** - Loads (or reloads) a config.
   - This is useful when a config for Argot is already defined. A config can list specific program targets and dataflow problems.
   - The config will specify which files contains existing user specified dataflow summaries
      (in the dataflow-problems > user-specs section, user-specs is a list of files)
   - If you need to add a new user-specs files in the config, you need to reload the config and the program to update the state of
     the mcp server.

1. **`argot_load`** - Load the program first (required)
   - Use the full path to the Go file: `argot_load ["/path/to/file.go"]`
   - For directories with multiple main functions, load individual files
   - When a config is loaded, `argot_load --target target_name` loads the target specified in the config.

2. **`argot_list_functions`** - List functions matching a regex
   - Use it to find the information of the function.
   - The user may have given imprecise package and function name information, this allows you to find the specific function.
   - You can search for <package_name>.*<function_name>.* or the like (use package to filter down).
   - If there are multiple choices, you must come back to the user to allow them to make a selection.
   - If you are summarizing an interface method, you can use the "interface_mode" option to list the implementations of an interface method.

3. **`argot_show_src`** / **`go doc -src -u`** - View the source code (primary tool)
   - Use function name regex: `argot_show_src <function_name>`, or `go_doc <query> src=true`
   - Use this for most functions -- source is easier to read than SSA, and calls are
     syntactically obvious
   - The `-u` flag of the `go doc` command shows documentation for unexported as well as exported
      symbols, methods, and fields.
4. **`argot_show_ssa`** (optional) - View SSA (Static Single Assignment) representation
   - Use function name regex: `argot_show_ssa <function_name>`
   - Only needed when source alone leaves ambiguity about exactly which field/value a line touches

5. **`argot_function_focus`** (optional) - Focus on specific function for detailed analysis
   - Use function name regex: `argot_function_focus <function_name>`
   - Enables use of value-specific analysis tools

6. **`argot_show_ssa_value`** (optional) - Examine specific SSA values (requires focused function)
   - Use SSA variable names from the SSA output (e.g., `t7`, `input`)
   - Shows type information, instruction details, and referrers
   - Helps trace how values flow through the function

## Step-by-Step Procedure

1. Load the program with `argot_load`
2. List matching functions / methods / interface methods with `argot_list_functions <function regex>` (optionally with interface_mode)
3. View source code with `argot_show_src`/`go_doc -src -u` to understand the function and identify callees
4. Repeat steps 2-3 for any callee that receives a value you can't otherwise be confident about
   (see "Workflow" above)
5. (optional) If source alone leaves ambiguity, view SSA with `argot_show_ssa`, focus with
   `argot_function_focus`, and examine specific values with `argot_show_ssa_value`
6. Generate the YAML dataflow summary based on your analysis
7. Write the summary with write_yaml_file, using exactly the filename given in the request
   (not a name based on the function/package)

## Required Arguments

To generate a dataflow summary, you need:

1. **File path** - A path to the main files of the program using the function. This is the path for the program to load, no the function to analyze.
2. **Function name** - Name of the function to analyze
3. **Package name** - Package containing the function

## Example Request

"Generate a dataflow summary for function `thisFunctionIsCalled` in file `/path/to/sample.go` in package `main`."

Generate only the YAML dataflow summary for the provided function. Do not include explanations unless the flow is complex and needs clarification.
